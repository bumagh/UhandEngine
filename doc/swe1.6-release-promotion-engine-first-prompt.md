# SWE1.6 多步骤提示词：从当前源码推进到可发布推广的 Web 应用（引擎化导向）

## 1. 文档用途

本文档用于让 `SWE1.6` 基于当前 `UhandEngine` 仓库状态，按步骤推进项目，从当前 Web-first MVP，逐步走到：

- 更清晰的 `Scene-first` 运行骨架
- 带有多个可演示的小游戏示例
- 可生产构建与发布的 Web 应用
- 具备对外推广和演示基础的项目交付状态

这个文档不是让模型一次性大改整个引擎，而是要求它 **分阶段、小步、可验证** 地前进。

## 2. 当前仓库基线

在开始执行之前，SWE1.6 必须理解当前基线：

- 当前项目是 `C + SDL2` 的轻量游戏引擎原型
- 已支持 Native 和 Web / Emscripten
- Web MVP 已可运行
- 当前 Web 页面已具备最小菜单场景与点击交互
- AI API 已通过本地脚本接入
- 已有 Scene Schema 示例与 AI 输出映射说明
- **第1周架构重构已完成**：
  - Scene 已使用 rootObject 替代 GameObjectList
  - GameObject 已使用父子关系（firstChild/nextSibling）替代链表
  - 平台层已抽象（platform.h/platform.c）
  - main.c 已适配新的 Scene 结构
- 当前主要问题不是“功能完全没有”，而是“架构仍偏原型，离可持续发布还有距离”

## 3. 最高优先级原则

SWE1.6 在整个推进过程中必须始终遵守：

1. 先稳定架构台阶，再扩展示例数量
2. 先让 `Scene` 成为更清晰的运行单元，再考虑更多玩法
3. 优先 Web 端交付，不要求同时把 Native 打磨到同等完成度
4. 所有改动必须小步、可验证、可回退
5. 不做无关重构
6. 不把更多随机功能继续堆进 `main.c`
7. 如果架构未准备好，优先补最小台阶，不一次性大改
8. 如果改动影响协作方式或产品交付方式，必须同步更新 `doc/`
9. API Key 不得写入源码、前端或仓库文件
10. 所有阶段都要围绕“能演示、能发布、能继续协作”来判断价值

## 4. 最终阶段目标

SWE1.6 的中期目标不是做完整引擎，而是在当前源码基础上完成以下结果：

- `Scene` 成为实际可感知的运行时组织单元
- 当前 menu demo 不再主要依赖 `main.c` 手工堆逻辑
- 至少有 2 到 4 个小游戏或微交互示例
- 示例可统一从 Web 入口访问
- Web 版本可以作为一个公开演示应用来构建和发布
- 文档中明确说明演示方式、验收方式、发布方式、下一阶段路线

## 5. 建议阶段划分

建议把整体推进拆为 6 个阶段。

### 阶段 A：运行骨架收敛

目标：

- 把当前 `main.c` 中的 demo 逻辑轻量下沉
- 给 `Scene` 一个更明确的运行时责任
- 为后续示例接入建立稳定入口

**注意：第1周架构重构已完成以下内容：**
- Scene 已使用 rootObject 替代 GameObjectList
- GameObject 已使用父子关系（firstChild/nextSibling）替代链表
- 平台层已抽象（platform.h/platform.c）
- main.c 已适配新的 Scene 结构

SWE1.6 在本阶段优先做：

- 利用已建立的 Scene-first 架构
- 将 main.c 中剩余的 demo 逻辑迁移到 Scene
- 为"当前场景"建立最小 owner 概念
- 保证现有 Web MVP 不回退

本阶段不要做：

- 完整 Scene 系统重写（已部分完成）
- 完整事件系统重写
- 完整资源系统重写

本阶段完成标准：

- `main.c` 更像平台入口，而不是直接堆 demo 内容
- 当前菜单场景仍可正常运行
- 新增边界清晰，便于继续挂接更多示例

### 阶段 B：最小示例框架建立

目标：

- 建立一套能持续增加示例的最小结构
- 让游戏示例不再是一次性代码

SWE1.6 在本阶段优先做：

- 定义“示例场景”组织方式
- 为每个示例明确入口、职责、资源依赖
- 建立最小的示例切换或示例注册机制
- 保持命名和结构对 AI 友好

推荐的示例方向：

1. `Main Menu` 菜单示例
2. `Click Counter` 点击计数示例
3. `Move Box` 键盘移动方块示例
4. `Simple UI Scene` 文本 + 按钮状态切换示例

本阶段完成标准：

- 至少可以稳定承载 2 个示例
- 新示例接入方式清楚、低成本
- 文档能说明如何新增第 3 个示例

### 阶段 C：补齐推广所需的小游戏示例

目标：

- 增加几个适合展示引擎方向的小游戏示例
- 让外部读者快速理解项目价值

SWE1.6 在本阶段优先做：

- 增加 2 到 4 个小示例
- 每个示例聚焦一个引擎能力点
- 示例保持轻量，不追求复杂内容

推荐示例能力组合：

- 示例 1：菜单与按钮
- 示例 2：输入与状态变化
- 示例 3：基础对象移动
- 示例 4：AI 生成场景草案映射展示

本阶段不要做：

- 大体量游戏
- 复杂美术资源接入
- 大量一次性玩法逻辑

本阶段完成标准：

- 示例足够说明项目方向
- 每个示例都有清晰演示点
- Web 页面中能形成较完整的展示集合

### 阶段 D：AI 协作链路升级

目标：

- 让 AI 输出不只是“旁路工具”，而是更自然地服务于示例与场景

SWE1.6 在本阶段优先做：

- 保持 `Scene Schema -> 当前代码结构` 的映射关系清晰
- 如条件允许，增加一个最小半自动映射步骤
- 继续强化 AI 提示词模板与输出约束
- 保持安全边界，不暴露 API Key

本阶段完成标准：

- 至少一条 AI 输出链路可重复演示
- 文档说明 AI 在发布版本中扮演什么角色
- 新代理可以顺着文档继续接手

### 阶段 E：Web 生产构建与发布准备

目标：

- 把当前项目从“本地可跑”推进到“可以生产构建和发布”

SWE1.6 在本阶段优先做：

- 梳理 Web 构建输出结构
- 检查静态资源路径是否稳定
- 确认构建产物可用于静态站点部署
- 补充发布所需说明文档
- 如有必要，增加一个统一的示例主页或说明页

推荐交付结果：

- 一份明确的发布步骤文档
- 一份部署说明
- 一份演示入口说明

本阶段完成标准：

- Web 产物可稳定重新构建
- 可部署到静态托管环境
- 新读者知道如何打开并试玩示例

### 阶段 F：推广与开源展示收口

目标：

- 让项目具备“可以对外展示和推广”的最小完成度

SWE1.6 在本阶段优先做：

- 收口 README 首页信息
- 补项目亮点、演示说明、示例说明
- 补发布版本说明或 MVP 发布记录
- 明确下一阶段路线图

本阶段完成标准：

- README 足够让外部读者理解项目
- 演示路径清楚
- 发布路径清楚
- 项目价值点清楚
