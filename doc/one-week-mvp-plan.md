# UhandEngine 一周 MVP 开发计划

## 1. 计划目标

目标是在 **1 周内交付一个最小可演示的 MVP**，并严格控制范围，保证能真正做出来、跑起来、演示出来。

本次 MVP 的核心目标不是“做完整引擎”，而是验证以下三件事：

- **Web 优先可用**
  - 优先让浏览器端可以使用 UhandEngine 跑起一个最小场景

- **AI 能力可接入**
  - 接入一个第三方 AI API，让引擎或配套工具具备最小 AI 能力

- **AI 协作闭环可验证**
  - 产出可供 `SWE1.6` 模型直接使用的提示词，使其能围绕当前仓库稳定地产生最小场景代码或规划结果

## 2. MVP 成功定义

一周后，MVP 至少需要满足以下条件：

- **浏览器可打开一个基于 UhandEngine 的最小场景**
- **场景中至少有一个文本对象和一个可交互对象**
- **项目可通过一个第三方 AI API 生成或辅助生成场景草案 / 场景代码骨架 / 配置草案**
- **有一组面向 SWE1.6 的稳定提示词模板**
- **有清晰的演示路径，能在 5 分钟内向他人说明“这个 MVP 已经可用”**

## 3. 本周必须严格限制的范围

为了保证一周内能交付 MVP，本周明确 **不做** 以下内容：

- 不做完整编辑器
- 不做完整 Physics 系统
- 不做完整 Animation / Tween 系统
- 不做完整资源管线重构
- 不做 Native 与 Web 双端同时打磨，**优先 Web**
- 不做大规模目录重构
- 不做大而全的 Scene DSL 完整实现

## 4. 本周 MVP 范围

本周只做以下最小集合：

### 4.1 Web 可运行最小引擎壳

目标：

- 浏览器可运行
- 有主循环
- 有最小渲染
- 有最小输入

最小能力：

- 一个 `Scene`
- 一个 `Text` 或文本显示能力
- 一个可点击区域或按钮能力
- 一个最小的场景初始化流程

### 4.2 最小 AI 接入能力

目标：

- 通过第三方 API 获取 AI 输出
- AI 输出至少能服务一种高价值任务

本周建议只做一个任务即可：

- **从自然语言生成场景草案**
- 或 **从自然语言生成对象列表 JSON**
- 或 **从自然语言生成 UhandEngine 示例代码骨架**

不建议一周内同时做三种。

### 4.3 SWE1.6 可用提示词

目标：

- 给 `SWE1.6` 模型一组明确、稳定、短链路的任务提示词
- 让它能基于当前仓库文档生成最小可用产物

本周建议只保证两类提示词可用：

- **生成最小场景骨架**
- **生成场景对象 JSON / Scene Schema 草案**

## 5. 推荐第三方 AI API 接入策略

为了控制一周交付风险，本周推荐采用 **单一第三方 LLM API**，不要同时接多个。

建议接入方式：

- 通过单独的小型服务层或代理层调用第三方 API
- 不要把密钥硬编码到前端页面或公开仓库中
- 优先使用环境变量或本地配置文件注入 API Key

### 5.1 推荐接入形态

建议本周采用以下形态之一：

- **方案 A：本地开发代理层 + 第三方 LLM API**
  - 浏览器端发请求到本地轻量服务
  - 本地服务再转发到第三方 AI API
  - 这是本周最稳妥方案

- **方案 B：仅本地工具脚本调用第三方 LLM API**
  - 不先集成到游戏页面里
  - 只做“输入描述 -> 生成 Scene Schema / 示例代码”的工具链
  - 这是最容易一周落地的方案

若目标是“确保一周能出 MVP”，建议优先选：

- **先做方案 B**
- 如果进度顺利，再补方案 A

### 5.2 安全要求

- **不要把 API Key 写进前端 JS / HTML / C 源码常量中**
- **不要把密钥提交到仓库**
- **使用环境变量或本地未提交配置文件**
- **在 README 或后续文档中明确说明需要用户自行配置 API Key**

## 6. MVP 推荐演示形态

为了让 MVP 能在一周内演示，推荐最终演示形式如下：

### 演示 1：Web 场景演示

在浏览器中打开 UhandEngine 的 Web 版本，展示：

- 标题文本
- 一个按钮
- 点击后改变文本或切换简单状态

### 演示 2：AI 生成场景草案

输入一段自然语言，例如：

```text
创建一个主菜单场景，包含标题 UhandEngine、一个 Start 按钮和一个 Settings 按钮。
```

AI 返回：

- Scene Schema 草案
- 或对象列表 JSON
- 或最小示例代码骨架

### 演示 3：SWE1.6 提示词效果

给 `SWE1.6` 一个固定提示词，让它根据仓库文档输出：

- 一个最小 Scene 代码草案
- 或一个最小 Scene Schema

## 7. 每日开发计划

## Day 1：收缩范围并冻结 MVP 规格

### 当日目标

把一周任务从“想做很多”收缩到“必须做成一个 MVP”。

### 重点任务

- 确认本周只做 Web-first MVP
- 确认 AI 接入只选一个第三方 API
- 确认 AI 能力只选一个核心用例
- 明确最终演示形式
- 写出 MVP 成功标准与非目标

### 当日产出

- 本文档定稿
- MVP 功能清单
- 非目标清单
- AI API 接入方案选择

### 完成标准

- 团队或自己能明确说出“本周只做什么、不做什么”

## Day 2：跑通 Web 最小引擎壳

### 当日目标

让 Web 端最小运行壳稳定可跑。

### 重点任务

- 验证 Emscripten/Web 构建链路
- 确认最小主循环可工作
- 确认页面能显示最小渲染结果
- 确认后续最小文本和点击交互能挂接进去

### 当日产出

- 可打开的 Web 演示页面
- 最小场景壳或场景初始化代码
- 已知 Web 问题清单

### 完成标准

- 浏览器中可稳定看到运行结果

## Day 3：做最小 Scene + Text + Clickable

### 当日目标

形成一个能演示“这是一个游戏引擎最小场景”的版本。

### 重点任务

- 挂接最小 `Scene`
- 增加最小 `Text` 显示能力
- 增加一个可点击对象或按钮
- 点击后改变文本、切换状态或触发最小事件

### 当日产出

- 一个可交互的 Web 场景
- 演示所需对象结构
- 最小场景说明

### 完成标准

- 演示页面至少具备“显示 + 交互”闭环

## Day 4：接入第三方 AI API

### 当日目标

打通 AI 请求链路。

### 重点任务

- 确定第三方 API 的请求格式
- 搭建本地代理或工具脚本
- 完成最小 Prompt 输入和输出
- 让 AI 输出一种可直接使用的结果：
  - Scene Schema
  - 对象 JSON
  - 示例代码骨架

### 当日产出

- 一个最小 AI 调用入口
- 一个最小可复用 Prompt
- 一个示例输入与输出样本

### 完成标准

- 能稳定得到一次有结构的 AI 返回结果

## Day 5：把 AI 输出接到 MVP 里

### 当日目标

让 AI 输出真正服务于引擎演示，而不是孤立存在。

### 重点任务

- 选择一个最简单的接入方式：
  - AI 输出 Scene Schema 草案，人工复制到示例中
  - 或 AI 输出对象 JSON，人工/脚本转换为场景初始化数据
- 让 AI 结果参与演示流程
- 固定一个可重复演示样例

### 当日产出

- 一条完整演示链路
- AI 输出到 MVP 的映射说明
- 最小用例文档

### 完成标准

- 演示时可以清晰说明 AI 在 MVP 中发挥了什么作用

## Day 6：准备 SWE1.6 提示词

### 当日目标

准备可直接用于 `SWE1.6` 的提示词集合。

### 重点任务

- 编写一组短提示词模板
- 明确输入格式、输出格式与约束
- 限制 SWE1.6 只做本周 MVP 需要的任务
- 验证提示词至少能稳定产出：
  - 最小 Scene Schema
  - 最小场景代码骨架

### 当日产出

- SWE1.6 MVP Prompt 模板
- 示例输入输出
- Prompt 使用说明

### 完成标准

- 至少有 2 个提示词模板可重复使用

## Day 7：联调、验收、录制演示路径

### 当日目标

把 MVP 收口成一个可演示的成果。

### 重点任务

- 联调 Web 场景与 AI 输出流程
- 修复阻断演示的问题
- 写 MVP 演示步骤
- 补充需要的说明文档
- 确定下一周继续迭代的最小方向

### 当日产出

- 一份最终演示步骤
- 一份 MVP 验收结果
- 下一阶段 backlog

### 完成标准

- 任何新读者在 5 分钟内能理解 MVP 的演示路径

## 8. 本周推荐技术路线

为了保证落地，本周推荐技术路线如下：

- **运行时方向**
  - 不做大重构
  - 在当前代码基础上补最小 `Scene`、最小 `Text`、最小 `Clickable`

- **平台方向**
  - **Web first**
  - Native 只保证不被当前规划破坏，不作为本周交付重点

- **AI 方向**
  - 只接一个第三方 LLM API
  - 只做一个最小高价值用例

- **文档方向**
  - 保持 `README`、`doc/`、`.windsurfrules` 同步
  - Prompt 文档只服务本周 MVP，不追求大而全

## 9. 本周建议的 AI 用例

建议本周只选以下其中一个：

### 用例 A：自然语言生成 Scene Schema

优点：

- 最贴合当前文档体系
- 最利于后续继续演进
- 最适合做 AI-first 引擎路线演示

### 用例 B：自然语言生成最小对象列表 JSON

优点：

- 结构比完整 Scene Schema 更简单
- 一周更容易稳定

### 用例 C：自然语言生成场景代码骨架

优点：

- 离运行时代码更近

缺点：

- 对 Prompt 稳定性要求更高
- 更容易生成与当前代码不一致的结果

**本周最推荐：用例 A，其次是用例 B。**

## 10. 面向 SWE1.6 的 MVP 提示词模板

以下模板专门为本周 MVP 准备，目标是限制输出范围，提高可用性。

## 10.1 Prompt：生成最小 Scene Schema

```text
你正在为 UhandEngine 生成一个最小 Web MVP 场景描述。

请严格遵守以下要求：
1. 项目是 C + SDL2 + Web(Emscripten) 的轻量游戏引擎原型。
2. 当前目标是 Web-first MVP，不要生成复杂系统。
3. 场景结构尽量符合 Scene-first 和 Phaser-like 2D 心智模型。
4. 只生成一个最小主菜单场景。
5. 场景中必须包含：
   - 一个标题文本
   - 一个 Start 按钮
   - 一个可选的 Settings 按钮
6. 输出格式必须为 JSON。
7. 字段尽量遵循 UhandEngine 的 `scene-schema.md` 文档。
8. 不要输出解释，只输出最终 JSON。
```

## 10.2 Prompt：生成最小场景代码骨架

```text
你正在为 UhandEngine 生成最小 Web MVP 的场景代码骨架。

请严格遵守以下要求：
1. 项目当前是 C + SDL2 + Web(Emscripten)。
2. 目标是最小 MVP，不要引入复杂框架。
3. 代码只围绕最小 Scene、Text、Clickable 能力展开。
4. 如果当前架构不足，请先用最小兼容方式接入，不要做大重构。
5. 保持命名清晰，尽量向 Scene-first、Phaser-like 方向靠拢。
6. 输出内容必须包含：
   - 需要新增或修改的文件
   - 每个文件的职责
   - 最小代码骨架
7. 如果某能力当前不存在，请明确标出最小补齐点。
```

## 10.3 Prompt：生成对象列表 JSON

```text
请根据以下需求，为 UhandEngine 生成一个最小对象列表 JSON：
- 一个标题文本：UhandEngine
- 一个 Start 按钮
- 一个 Settings 按钮
- 风格简洁
- 用于 Web MVP 演示

要求：
1. 输出必须是 JSON。
2. 每个对象应包含：id、name、type、transform、components。
3. 尽量与 `scene-schema.md` 兼容。
4. 不要输出解释。
```

## 11. 风险与应对

### 风险 1：想做太多，导致一周内没有可演示结果

应对：

- 严格冻结 MVP 范围
- 每天只追一个关键结果
- 所有非 MVP 能力一律放入 backlog

### 风险 2：AI API 接入花费时间超预期

应对：

- 优先做本地脚本或本地代理层
- 不把前端直连第三方 API 作为第一方案
- 必要时先做“离线调用 -> 保存结果 -> 导入演示”的半自动流程

### 风险 3：Web 端调试消耗过多时间

应对：

- 优先保证最小场景能展示，不追求 UI 完整美观
- 先做最小文本和点击交互闭环
- 不在本周处理所有平台细节

### 风险 4：SWE1.6 输出不稳定

应对：

- 严格限制 Prompt 输出范围
- 明确输入输出格式
- 优先要求输出 JSON 或结构化骨架

### 风险 5：API Key 安全问题

应对：

- 不在前端暴露密钥
- 不提交密钥到仓库
- 本地环境变量管理

## 12. 本周交付物清单

本周结束时，建议至少产出：

- 一个 Web 可演示 MVP
- 一个最小可交互场景
- 一个第三方 AI API 接入样例
- 一组面向 SWE1.6 的 MVP 提示词
- 一份 MVP 演示说明
- 一份下一周 backlog

## 13. 本周验收标准

满足以下条件即可视为一周 MVP 达标：

- 浏览器中可运行最小场景
- 场景具备文本显示与点击交互
- 第三方 AI API 能成功返回结构化结果
- 至少一个 AI 输出参与了 MVP 演示流程
- SWE1.6 提示词可复用
- 新人可在短时间内理解如何演示该 MVP

## 14. 结论

这一周的目标不是把 UhandEngine 做成完整 AI 游戏引擎，而是要用 **最小范围** 验证一条真正可行的产品路线：

- 引擎可以在 Web 上先跑起来
- AI 能力可以真正接进来
- SWE1.6 可以围绕既有文档稳定协作

只要这一周做到了这三点，这个 MVP 就是成功的。
