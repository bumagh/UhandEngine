# UhandEngine AI Agent Workflow

## 1. 文档目标

本文档定义 AI 编码代理在 `UhandEngine` 仓库中的标准协作流程。

目标是让 AI 在参与此项目时：

- 先理解，再修改
- 保持 Scene-first 与 PhaserJS 对齐方向
- 只做小步、可验证、可追踪的变更
- 把文档、规则和代码视为同等重要的产品组成部分

## 2. 适用范围

本流程适用于以下任务类型：

- 架构梳理
- 文档补充
- 小步重构
- 新模块设计
- 运行时能力接入
- AI 规则与 Prompt 体系维护

## 3. 总体工作流

建议 AI 按以下顺序执行任务：

```text
1. 明确任务目标
2. 阅读相关文件
3. 总结当前结构
4. 判断是否需要补文档或计划
5. 设计最小可行改动
6. 实施改动
7. 同步相关文档
8. 总结影响与下一步建议
```

## 4. Step 1：明确任务目标

AI 开始工作时，必须先判断任务属于哪一类：

- 文档类
- 规则类
- 架构类
- 代码实现类
- 调试类

并明确以下问题：

- 用户要的是“方案”还是“直接落地”
- 是否涉及现有核心模块
- 是否会触及架构边界
- 是否需要同步更新文档

## 5. Step 2：阅读相关文件

AI 在修改前必须读取相关文件。

优先阅读顺序建议：

1. `README.md`
2. `doc/architecture.md`
3. `.windsurfrules`
4. 与任务相关的模块源码或文档

如果任务涉及架构与 AI 协作，还应阅读：

- `doc/scene-schema.md`
- `doc/component-contract.md`
- `doc/runtime-api.md`
- `doc/swe1.6-prompt-and-skills.md`

## 6. Step 3：总结当前结构

在做较大变更前，AI 应先给出简短结构总结：

- 当前模块位置
- 当前数据流或控制流
- 与任务直接相关的边界
- 潜在风险点

总结要求：

- 简洁
- 可执行
- 不空泛

## 7. Step 4：判断是否需要计划与文档先行

当任务满足以下情况之一时，应先建立轻量计划：

- 涉及多个文件
- 涉及文档 + 代码联动
- 涉及架构边界变化
- 涉及中等以上规模修改

当任务满足以下情况之一时，应先补文档或同步文档：

- 改动影响模块职责
- 改动引入新抽象
- 改动改变 AI 工作方式
- 改动改变 Scene / Component / API 契约

## 8. Step 5：设计最小可行改动

AI 应优先选择：

- 最小补丁
- 最小新文件集
- 最小重构路径

而不是：

- 大规模无计划改名
- 不必要的目录搬迁
- 把多个问题一次性混改

判断标准：

- 是否保留 PC + Web 双端兼容
- 是否保留现有运行逻辑
- 是否更贴近 Scene-first
- 是否更贴近 Phaser-like 2D 心智
- 是否更适合 AI 后续接力

## 9. Step 6：实施改动

实施阶段的规则：

- 先做与任务最直接相关的改动
- 不做无关重构
- 若发现当前架构不足以承接需求，先补最小架构台阶
- 代码改动时优先保持接口稳定
- 文档改动时优先保持索引完整和术语统一

## 10. Step 7：同步文档

以下场景必须同步文档：

- 新增长期维护文档
- 修改运行时 API 方向
- 修改 Scene / Component 契约
- 改变目录结构
- 引入新的 AI 协作规范

优先同步位置：

- `README.md`
- `doc/architecture.md`
- 对应专题文档
- `.windsurfrules`

## 11. Step 8：输出总结

AI 每轮任务结束时应总结：

- 完成了什么
- 改动了哪些文件
- 风险点或未完成项
- 建议的下一步

## 12. 文档类任务工作流

适用于：

- 架构说明
- 路线图
- Schema 设计
- 协议定义
- Prompt / Skills / Rules 文档

建议流程：

```text
阅读现有文档
→ 识别缺口
→ 生成新文档
→ 同步 README / architecture 索引
→ 总结用途和后续关联文档
```

## 13. 代码类任务工作流

适用于：

- 新模块接入
- 小步重构
- 运行时修正
- API 收敛

建议流程：

```text
阅读相关源码
→ 识别调用链与职责边界
→ 判断是否需先补文档
→ 实施最小补丁
→ 检查受影响模块
→ 同步文档
→ 总结风险
```

## 14. 架构类任务工作流

适用于：

- Scene-first 接入
- GameObject / Component 边界调整
- InputManager / AssetManager 抽象
- PhaserJS 对齐相关设计

建议流程：

```text
先读 README + architecture + rules
→ 读核心源码
→ 总结当前架构
→ 给出最小架构台阶
→ 优先文档化
→ 再实施小步代码改动
```

## 15. 调试类任务工作流

适用于：

- 崩溃修复
- 生命周期异常
- Web / Native 不一致问题
- 输入与渲染问题

建议流程：

```text
先定位现象
→ 阅读相关调用链
→ 判断根因而非表面症状
→ 仅在确认方案后修改代码
→ 必要时加更清晰日志
→ 总结根因与修复范围
```

## 16. AI 禁止事项

AI 在本仓库中应避免：

- 未读相关文件就直接大改
- 做无关重构
- 把架构逻辑继续堆到 `main.c`
- 破坏 PC / Web 双端兼容
- 不同步文档就修改关键架构
- 设计难以让后续 AI 继续理解的接口

## 17. AI 优先事项

AI 应优先推进：

- `Scene` 成为真实运行时拥有者
- `GameObject` / `Component` 关系清晰化
- `Transform` 向 2D-first 升级
- `AssetManager` 与 `InputManager` 抽象
- `Text` / `Sprite` / `Container` 的 Phaser-like 方向
- 文档、规则、Prompt 与 Skills 的长期维护

## 18. 推荐的任务输出结构

建议每次任务输出包含：

1. 当前判断
2. 实施内容
3. 影响文件
4. 风险点
5. 下一步建议

## 20. 结论

`AI Agent Workflow` 文档的核心价值，不是限制 AI，而是让 AI 在这个仓库中形成稳定、可继承、可扩展的工作方式。

这样每次修改都更容易：

- 对齐项目方向
- 保持文档一致
- 控制改动风险
- 为后续 Agent 继续接力保留上下文
